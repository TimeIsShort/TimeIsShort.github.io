从旅游规划 Bot 到 AI 接单团队：我用 Grok Bot 搭了一套个人 Agent 工作流

从旅游规划 Bot 到 AI 接单团队：我用 Grok Bot 搭了一套个人 Agent 工作流

最近我一直在折腾 Grok Bot。

最开始其实只是一个很简单的想法：能不能做一个私人旅行社？

我输入假期、出发城市、预算和偏好，几个 Bot 自己分工：

  • 有人负责筛目的地；
  • 有人负责查高铁、机票和总交通成本；
  • 有人负责找住宿区域和酒店；
  • 有人负责规划景点、美食和每日路线；
  • 最后再由一个总控 Bot 汇总并做决策。

结果越做越发现，这个思路根本不应该只用来规划旅游。

它完全可以继续延伸到软件开发、知识库、任务管理，甚至是自由职业接单。

这篇文章记录一下我最近形成的一套思路：从“一个 AI 助手”，走向“一支 AI Agent 团队”。

一、第一版：先给自己搭一个 AI 私人旅行社

我最开始设计了 5 个 Bot。

Bot 职责 核心问题
Travel Chief 总控、汇总、最终决策 最后怎么选
Destination Scout 筛选目的地 去哪里
Transport 高铁、火车、飞机、自驾比较 怎么去
Hotel 住宿区域、酒店筛选 住哪里
City Guide 景点、美食、路线、每日行程 怎么玩

例如我输入：

国庆 4 天，从杭州出发，两个人，预算 5000，不想太累，喜欢自然风景和美食。

理想的工作流不是让 5 个 Bot 一起乱搜，而是分阶段执行。

这个设计很快让我意识到一个问题：

多 Agent 最难的并不是“每个 Bot 会不会干活”，而是谁负责调度。

二、再加一个 Coordinator：让专业 Bot 不要自己开会

如果完全放任多个 Bot 相互调用，很容易出现这种情况：

最后一群 Bot 自己聊得很热闹，调用量很高，但产出的信息大量重复。

所以我后来又加了一个：

Travel Coordinator

它不负责研究旅游内容，只负责工作流。

它做的事情是：

  1. 把用户需求整理成统一上下文；
  2. 判断本次到底需要哪些 Bot；
  3. 按阶段派任务；
  4. 防止重复研究；
  5. 收集结果；
  6. 最后交给 Travel Chief 做决策。

于是整个结构变成了：

这里我开始总结出一个很重要的 Agent 设计原则：

Coordinator 管流程，Expert Bot 管专业问题，Chief 管最终决策。

不要让所有 Agent 都既是专家、又是项目经理、又是审批人。

三、旅游工作流跑通之后，我突然想到：开发工作为什么不能这么干？

这才是后面真正有意思的部分。

我平时做后端开发，实际工作链路经常是：

如果把这个流程 Agent 化，它完全可以变成：

这时候我自己真正需要做的事情就变了。

以前是：

我亲自完成流水线上的每一步。

以后可能变成：

我负责判断需求、风险、方案和最终审批。

四、知识库会成为整个 Agent 团队真正的大脑

如果 Agent 每次处理任务，都要重新解释：

  • 这个需求在哪个微服务；
  • 哪个仓库；
  • 哪个版本分支；
  • 哪些表有关；
  • 以前有没有类似 Bug；
  • 哪些代码千万不能乱改；

那 Agent 虽然会写代码，但依然很低效。

所以我越来越觉得，真正重要的并不是单独某一个模型，而是：

Knowledge Bot 可以在每次开发前先给 Agent 一份上下文：

这样 Claude 和 Codex 不需要每次从零开始理解整个项目。

而每次修复完成后：

下一次再遇到类似问题，Agent 又能直接复用。

这就是我很看重的一个东西：

上下文复利。

模型会换，模型能力会越来越强，但自己积累下来的项目知识不会白费。

五、然后思路又继续往前走了一步：能不能让 Agent 自己找开发任务？

有一天我突然想到：

既然 Grok Bot 本身就是一个可以长期运行、能用浏览器和云电脑的 Bot，那么它为什么不能帮我在自由职业平台找开发任务？

于是我又设计了一个：

Dev Job Scout

它不是无脑搜索“Java”然后把几十个任务丢给我，而是负责：

最终只保留真正值得看的几个任务。

比如：

这和普通的“职位搜索”完全不一样。

我想要的不是：

找到最多的任务。

而是：

找到我成功率最高、单位时间收益最好、风险最低的任务。

六、真正需要判断的，不只是“我会不会做”

在 Upwork 上看了一些任务之后，我发现筛单本身就是一门技术。

比如一个 SQL Server 数据库恢复任务：

如果备份本身没加密、版本兼容、文件正常，它的任务边界其实非常明确。

这种任务即使不是我最熟悉的技术栈，也比较容易评估风险。

反过来，我又看到一个 Java/Spring/AWS 项目：

Complete the existing application
Fix existing bugs
Complete CI/CD
Fix failing tests
Review the code and improve it

表面看：

Java + Spring，技术匹配度很高。

但仔细看客户历史，却发现以前已经找过人修过同一个项目，现在又重新发布类似任务。

这就出现了一个非常危险的信号：

上一次可能只是把症状压下去了，没有解决根因。

这种任务很可能进去以后变成：

而报价仍然可能只是一个普通小项目价格。

这让我总结出一个非常有用的筛单规则：

“我能做”不等于“这个单值得接”。

Job Scout 应该额外检查：

  • 最近是否发布过相同任务；
  • 上一次是否已经显示完成；
  • 是否很快又重新出现；
  • 描述是否越来越模糊；
  • 是否仍然维持原来的低预算；
  • 是否存在明显 Legacy / Technical Debt 信号。

如果命中多项：

这种任务即使技术匹配 95%，也应该降低优先级。

七、新账号最重要的不是赚最多，而是先建立“成功记录”

刚开始做自由职业时，我原本会自然地认为：

金额越高的单越值得投。

但实际上完全不是这样。

对于一个没有平台历史的新账号，我现在更倾向于：

比如：

方案 A

方案 B

第一单我一定更愿意接 A。

因为我要的是：

一个能稳稳完成、让客户愿意给五星评价的漂亮交付。

而不是第一单就去接一个历史烂项目。

所以：

可以接便宜一点的好单，但不要接便宜又麻烦的垃圾单。

八、Connects 本质上不是“点数”，而是获客成本

自由职业平台投标并不是零成本。

当每个 Proposal 都需要消耗一定资源之后，我的思路也从：

“这个任务看起来还行，要不要投？”

变成：

“这个任务值不值得花获客成本？”

于是 Job Scout 就可以把这一步也纳入评分：

只有达到标准的任务，才进入：

值得投标

列表。

这其实和做广告、销售获客没什么区别。

九、为什么 AI 已经会做很多任务，客户还愿意付钱？

这是我在看这些任务时觉得最有意思的问题。

有些任务，从技术动作上看，Claude、Codex 甚至普通 AI 已经可以完成很大一部分。

那为什么客户不自己问 AI？

后来我越来越觉得，客户真正购买的通常不是：

“有人帮我敲几百行代码。”

而是：

有人把我的问题解决，并对结果负责。

非技术客户往往只能描述：

网站有点慢。
登录偶尔失败。
数据不对。
帮我加个功能。
数据库恢复不了。

他们不知道应该继续问：

而一个真正懂技术、又会使用 AI 的人，会先把模糊问题变成一个 Agent 能执行的工程任务。

然后再完成：

所以未来很可能真正拉开差距的，不是谁比 AI 更会敲代码，而是谁更会：

定义问题、调度 AI、判断结果、承担责任。

十、我最终想做的，是一套“AI 开发公司”

如果继续沿着这个方向往下做，我脑子里的最终结构大概是这样：

这里最重要的不是“全部自动”。

恰恰相反，我认为必须保留几个明确的人类审批点：

必须人工确认

  • 是否接单；
  • 是否承诺工期；
  • 是否接受报价；
  • 高风险代码是否合并；
  • 是否操作生产环境；
  • 是否付款；
  • 是否最终交付。

可以高度自动化

  • 找任务；
  • 初筛；
  • 技术分析；
  • 拉取知识；
  • 创建分支；
  • 编码；
  • 测试；
  • Review；
  • 写修复说明；
  • 更新任务状态；
  • 写日报/周报；
  • 知识沉淀。

我想要的不是一个“完全失控的自动化系统”。

而是：

AI 负责执行，人负责授权和承担责任。

十一、我的角色也在发生变化

这套东西真正让我觉得有意思的，不是“以后可以少写几行代码”。

而是我的工作角色可能会发生变化。

以前：

以后：

我会越来越像：

产品经理 + 技术负责人 + Reviewer + Agent Manager。

甚至可以开个玩笑：

再这样折腾下去，我不是在写代码，我是在给 Claude、Codex 和一群 Bot 当老板。

但仔细想，这可能并不完全是玩笑。

十二、最后：AI 时代真正稀缺的可能不是“会不会写代码”

我现在越来越认同一件事：

AI 会让很多具体技术动作变便宜。

写 CRUD 会越来越便宜。

写 SQL 会越来越便宜。

搭接口会越来越便宜。

甚至排查很多 Bug 也会越来越便宜。

但与此同时，另外几种能力会越来越重要：

  1. 能不能理解真正的问题；
  2. 能不能把复杂问题拆成可执行任务；
  3. 能不能给 Agent 提供正确上下文；
  4. 能不能判断 AI 输出是否靠谱；
  5. 能不能设计一个稳定的协作流程；
  6. 能不能承担最终结果。

所以我现在折腾 Grok Bot、Claude、Codex、知识库和这些工作流，并不是为了证明：

AI 可以替我写代码。

而是想看看另一种工作方式到底能走多远：

一个人，能不能通过一套 Agent 系统，把自己的产能放大成一个小团队。

目前来看，我觉得这件事比单纯换一个“更聪明的模型”有意思得多。

下一步，我准备继续把：

这条链路真正跑通。

如果它最终能稳定工作，那时候我卖的可能就不再只是：

“我的开发时间”。

而是一整套：

AI Agent + 工程经验 + 知识库 + 自动化流程

带来的交付能力。

这可能才是我真正想构建的东西。
